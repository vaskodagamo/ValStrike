**Scope:** deterministic native C++17 `ValStrike::Rules::MatchRules`, with a four-slot connected roster, two persistent teams capped at two, configurable one/two-player minimum, six rounds, a role swap after three completed rounds, all objective/elimination wins, draw and explicit rematch. Defaults remain 8 s preparation, 90 s active, 3 s plant, 5 s defuse, 30 s detonation. No Unreal actors, shared contracts, map assets, configuration or module dependencies are changed.

**API and ownership:** the future authoritative GameMode owns one model for its server lifetime. Construct with `Config`; invalid configuration leaves a safe waiting model with `ConfigurationValid == false`, and `Apply` rejects all frames. `Read()` exposes a const snapshot. `Apply(Frame)` consumes a sealed timestamped batch and returns per-event statuses plus one-time `Effect`s. Standard-library arrays/vectors are the only supporting types; no exceptions, RTTI, third-party dependency or generic event framework is required. The model is single-threaded; the adapter serializes calls on the game thread.

`Snapshot` exposes phase, persistent attacking/defending team, scores, completed rounds, current round identity, round winner/reason, explicit match result including draw, phase deadline, connected roster, participant/alive flags, device state/revision/carrier/site, and interaction token/start/completion. `RosterCount`, `ParticipantCount` and `LivingCount` distinguish session membership from this round's combatants. `CanMove`/`CanCombat` require Active/Planted plus a living participant; all other phases and late spectators are gated off. World eligibility is deliberately not a cached snapshot claim: a current interaction records the last validated actor, while continuity must be supplied again for every advance.

**Time and request rules:** time is nonnegative integer server milliseconds. Quantize once in the adapter, using a monotonic server clock; never use client timestamps. Every accepted `Frame.Now` strictly increases, including frames without events. Aggregate all callbacks that share the same millisecond into one sealed batch before calling `Apply`; a second frame at an already processed millisecond is rejected atomically. `Sequence` is a server-issued increasing value from 1 through `MaxSequence`, retained across rematches and abandoned-match clears. Frame rejection does not consume sequence/time or cancel an interaction. A valid frame containing a rejected individual event still advances time and can produce timed outcomes.

Durations must be positive and at most 86,400,000 ms; minimum roster must be 1 or 2. Durations need not be shorter than their applicable deadline (an impossible-to-finish plant/defuse is allowed tuning and loses to the deadline). Accepted server time is bounded by `INT64_MAX - 4 * MaxDurationMs`; deadline additions stay in range rather than wrapping or saturating. The adapter must treat exhaustion of time/sequence space as a server lifecycle error. These limits are far beyond a practical server lifetime.

The server assigns nonzero connection IDs monotonically; successful joins advance a high-water mark. Never reuse an ID after disconnect, including on rejoin/rematch. Team assignment is explicit, validated and permanent for that connection. Admissions in a batch are processed in ascending ID order, so the lower ID gets the last team slot. Per-player `RequestId`s for Drop/Retrieve/StartPlant/StartDefuse/StopInteraction must increase and are retained across rounds/rematches; fresh requests with valid actor/round consume the request ID even if later rejected for phase, eligibility or device state. Every non-roster event must identify the current nonzero `RoundId`. Device operations additionally require a current revision; stop requires the current interaction token. Late/stale data cannot act on a new round, connection, placement or interaction.

Each batch allows at most 16 events, one roster event per connection, one death per connection, one voluntary action per connection, one world placement/recovery event and one next-round/rematch control. Ambiguous duplicates and unknown event kinds reject the whole batch. Death plus release is legal. Client retry suppression/ownership checks remain the adapter's job before assigning these server-side IDs.

**Deterministic ordering:** first cancel any uncertified existing interaction at the previous model time, then process all deadlines strictly before the new time in chronological order. A plant strictly before the active deadline replaces that deadline; detonation can then be processed during the same large advance. At the endpoint, aggregate deaths/disconnects in ascending connection-ID order. An abandoned empty server clears immediately without awarding an additional point. If preparation loses its minimum participant count, cancel it without a score award. Apply explicit release/drop/recovery invalidations, then the hard phase deadline, then aggregate elimination, then other actions and any interaction completion. Consequently:

- A hard round/detonation deadline defeats completion at an exact tie and also defeats an elimination at that same time.
- Release, range/held invalidation, death, disconnect or device loss at a completion timestamp defeats that completion. An earlier completed interaction remains earlier than a later event if continuity was certified over the interval.
- Simultaneous preplant mutual elimination awards defenders; postplant mutual elimination awards attackers. Postplant attacker elimination alone leaves the device running. At a completion timestamp elimination takes priority over plant/defuse completion; no point is awarded twice.
- Lowest connection ID wins contested pickup/defuse start. Repeating a valid start by its current actor is unchanged and cannot refresh its start time. A fresh repeated start with false world eligibility or an invalid site cancels that actor's progress. A stale/replayed command cannot masquerade as a fresh release; send an actual fresh invalidation.
- Death/action validation at the exact preparation boundary uses the preparation gate before activation. The adapter must not report preparation damage. Gameplay becomes eligible from the resulting Active snapshot.

**Continuous eligibility obligation:** `Frame.ContinuousInteractionToken` is an explicit certificate that the current interaction stayed held and eligible throughout the elapsed interval, except for endpoint invalidations included in that batch. It must match the existing interaction token; omission/mismatch cancels at the previous `Snapshot.Now` before catch-up. A fresh proximity sample at a late tick is insufficient. Subscribe to release, death, disconnect, movement/range/site changes and any world obstruction/placement conditions used by the interaction validator; break continuity immediately when any condition fails. Use a fresh `StopInteraction` event for known invalidation at the endpoint. If the adapter cannot establish the uninterrupted interval, omit the certificate and require a new start, losing progress. Do not split simultaneous invalidation and completion across calls or backdate completion from a client claim. Keep `WorldConfirmed` server-derived: plant requires living attacker/carrier in authored site A, defuse requires living defender near the planted device, retrieve requires a reachable dropped device within range. Role/life/ownership/phase/revision are also rechecked by the core.

**Roster and flow:** preparation freezes round participants and emits a new `RoundId`; all roster members then start alive. Joins during an existing preparation, active/planted round, resolution or match completion are spectators until a new preparation. The lowest-ID attacker initially carries the device. A preparation that loses the minimum number of participants aborts to Waiting; a qualifying connected roster may immediately start a fresh preparation in the same frame, legitimately admitting previous spectators. During an active round, disconnect removes the living participant and can resolve elimination. Before another round, insufficient roster enters Waiting with scores/completed rounds preserved. When both teams qualify, preparation resumes. Empty-server clear precedes new admissions in the same batch and resets abandoned match score, roles, result, device and participants while preserving anti-replay high-water marks.

There is no invented result-screen duration. `Resolved` stays locked until the server explicitly sends `NextRound` for that round. Controls are processed after the timestamp's outcomes, so the server may intentionally combine continuation with a resolving batch; ordinarily wait for the award snapshot/effects before sending it. The sixth award goes directly to `MatchComplete` even after a 4–0 lead. `Rematch` is valid only there and clears scores/results, restores Team One attacking, preserves connections/team membership/request high-water marks, and starts preparation if the roster qualifies. Roles change at the next preparation after the third award, preserving the just-finished round's role in its resolved snapshot.

**World effects:** each output has a lifetime-unique `EffectId = Sequence * 64 + ordinal` and logical `At`, round identity, relevant player/team and device revision. Frames produce fewer than 64 effects. Logical times and gameplay results are independent of tick size; effect IDs may differ if callers choose a different frame sequence partition. Apply effects once in returned order and deduplicate by ID if the integration queues/retries delivery. They are not a persistent queue or database; the adapter must retain a returned batch until applied. Snapshot replication must not replay one-time effects. A valid rejected-event frame can still contain effects; always process `StepResult.Effects`.

`PrepareRound` requires actual authoritative respawn/health/ammo/fixed-loadout reset, transient cosmetic reset, role-based spawn selection and device attachment. `WaitingForRoster` cancels pending placements/interactions and gates players. `MatchCleared` clears the world objective and all match transient state. `RoundAwarded` is a single server-side notification; scores are already updated in the snapshot, so do not add the point a second time. `RoundActivated` opens the gates. `DevicePlanted`, `DeviceDefused`, `DeviceDetonated` and interaction effects drive the objective actor/presentation. Resolved/match-complete snapshots lock later combat/objective actions.

Drop, carrier death/disconnect and recovery emit `DropPlacementRequested` or `RecoveryPlacementRequested`, entering `PlacementPending`. The core never invents transforms. The adapter validates a reachable drop location near the previous carrier, falling back to the designated recovery marker if needed, or explicitly uses that marker for recovery. Once physical placement is successful and reachable, send `ConfirmPlacement` with the current round/revision and server `WorldConfirmed = true`; only then is the device Dropped/retrievable. `RecoverDevice` is a server-confirmed out-of-play/reachability event, allowed for carried/dropped devices, not a means to move a planted device. An already pending device cannot issue duplicate recovery. Async stale placement acknowledgements fail revision/round checks. Suppress obsolete placement work when its round/device revision is no longer current or its phase is resolved; a last-life carrier drop may be followed by a same-batch award. Failed placement must be retried by the adapter at the designated recovery point; never falsely acknowledge it.

Map integration uses MAP_BRIEF.md schema version 1: site ID A, two attacker and two defender spawn roles, `VS_DeviceRecovery`, and authored playable/site bounds. Load/validate that metadata outside this core, map persistent team identities to current spawn roles, and supplement simple bounds with actual reachability checks. No JSON/world transform/map loader belongs in the model.
